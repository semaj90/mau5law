rt answer: not necessarily — QUIC (HTTP/3) requires TLS on the external connection, but that TLS can be terminated by Caddy. Qdrant itself does not have to enable TLS on its gRPC port if Caddy is terminating TLS/QUIC and then proxying to Qdrant over an internal (insecure) connection. What matters is how Caddy is configured to talk to the upstream.

What to consider and recommended setups

QUIC/HTTP‑3 requires TLS 1.3 on the wire. Clients speaking QUIC will perform the TLS handshake as part of QUIC. Caddy can be the TLS/QUIC terminator (this is the common and recommended pattern).
If Caddy terminates TLS/QUIC, it will open a plain (or HTTP/2 / h2c) connection to the backend. In that case it is safe for Qdrant to have TLS disabled as long as:
Caddy and Qdrant are on the same host or a trusted internal network.
You don’t expose Qdrant’s ports directly to the public internet.
If you want end‑to‑end TLS (Caddy just forwards encrypted traffic without terminating it), then Qdrant must be listening with TLS enabled. That is uncommon when using a reverse proxy like Caddy, and can be harder to manage.
Common Caddy reverse‑proxy patterns for Qdrant

Caddy terminates TLS/QUIC (recommended). Caddy serves HTTP/3 to clients and proxies to Qdrant’s HTTP (6333) and gRPC (6334) backends. For gRPC you want Caddy to speak h2c to the upstream.
Example Caddyfile (informational):

qdrant.example.com { # HTTP API -> Qdrant HTTP (6333) reverse_proxy localhost:6333 { # keep default behavior for normal HTTP header_up X-Forwarded-Proto {scheme} }

}

Notes:

The crucial bit for gRPC is transport http { versions h2c } so Caddy speaks HTTP/2 cleartext (h2c) upstream. If Caddy is terminating TLS, you do not need TLS enabled on Qdrant.
If you instead proxy the HTTP API (port 6333) through Caddy, that can remain plain HTTP upstream as above.
If you need direct TLS on Qdrant (less common)
Enable TLS on Qdrant (via its config / docker options). Then Caddy can use TLS when proxying (or you can bypass Caddy and let clients talk directly). This gives end‑to‑end encryption but requires certificate management on the Qdrant instance.
Why you saw "TLS disabled for gRPC API"

That log line means Qdrant is listening unencrypted. That’s fine if Caddy is terminating TLS upstream and you don’t expose Qdrant directly.
If you see header parse errors in Qdrant logs (actix invalid Header), that often indicates the reverse proxy sent HTTP/3 or HTTP/1.1 framing that the backend didn’t expect — make sure Caddy is configured to talk h2c for gRPC upstream and not send a mismatched protocol.
Security recommendations

If Caddy and Qdrant run on the same host / internal Docker network, leaving TLS off for Qdrant is acceptable and simpler.
If Qdrant is accessible on an untrusted network, enable TLS on Qdrant or restrict access with firewall rules / network policies.
Log/monitor for parse errors — they’ll hint at protocol mismatches between Caddy and the backend.
